# Безопасный переход на связи спектаклей по ID

## Что меняется

Миграция `0026_legacy_performance_credits` создаёт только новую таблицу журнала
переноса. Она не переносит данные автоматически, не удаляет столбцы и не меняет
записи актёров, режиссёров, фотографий или биографий.

Актёрские роли читаются из существующего `PerformanceCast`, постановки режиссёра —
из `Perfomances.director`. Новый журнал сохраняет исходные значения старой записи,
её индекс и связанную постановку. Названия/роли и годы/коллективы в старых массивах
остаются в базе, включая несопоставленные значения и лишние элементы массивов.

Новый режим выключен по умолчанию: `PERFORMANCE_RELATIONS_ENABLED=False`.
Применение миграции таблицы само по себе не переключает сайт и не запускает перенос.
В старом режиме также добавлены защитные проверки: сохранение биографии с неизменными
массивами не пересинхронизирует состав; неизвестное/неоднозначное название и разные
длины массивов отменяют правку ролей; редактирование исторических ролей не удаляет
состав будущих показов.

## Предварительный анализ

Из `backend/app`:

```sh
USE_MINIO_STORAGE=False ../venv/bin/python manage.py link_legacy_performances --report /tmp/relationships-review.json
```

Без `--apply` команда только читает базу. Отчёт создаётся новым файлом с правами
0600, существующий файл не перезаписывается. Не коммитьте отчёты с рабочими данными.
`digest` учитывает все поля людей, спектаклей, состав и существующий журнал.

Сопоставление использует только точное совпадение названия с одной активной записью
вне афиши; у режиссёра также учитывается точное `production_title`. Нет fuzzy search,
извлечения названий из кавычек или выбора «первой» записи. Неизвестные/повторяющиеся
названия, удалённые люди, недостающие роли, конфликтующие режиссёры или разные
исторические постановки с одним названием остаются для ручного разбора.

## Проверка на копии и применение

До production необходимы свежий приватный backup и проверенное восстановление в
отдельную базу. На копии сначала выполните анализ, разберите отчёт, затем:

```sh
USE_MINIO_STORAGE=False ../venv/bin/python manage.py link_legacy_performances --apply --expected-digest <digest-из-отчёта>
```

Команда откажется, если состояние базы отличается от проверенного отчёта.
На время импорта блокируются изменения затрагиваемых таблиц (обычное чтение может
продолжаться), чтобы новые дубли названий не появились между проверкой и записью.
Для production выбирайте окно обслуживания. Ошибка прерывает всю транзакцию.

Импорт добавляет журнал и недостающие строки состава. Существующие строки состава
не удаляются. Режиссёр назначается только если FK пуст и соответствие однозначно;
существующий другой режиссёр не заменяется. Поля актёров и режиссёров не сохраняются
вообще. Для повторного применения нужен новый отчёт/digest; дубликаты не создаются.

Неоднозначные строки автоматически не исправляются. Их исходные значения остаются
в прежних полях и отображаются как исторические записи без предполагаемой ссылки.

## Переключение чтения

После проверки копии и отдельно согласованного применения в рабочей базе задайте
backend-переменную `PERFORMANCE_RELATIONS_ENABLED=True` и перезапустите backend.
Фронтенд использует добавленное поле `performance_credits`, если оно присутствует;
без него остаётся старый интерфейс. Отдельный frontend-флаг не нужен.

В новом режиме:

- ссылки ведут по ID и сохраняются после переименования;
- состав и роли редактируются в спектакле, постановка режиссёра — в его карточке;
- старая двусторонняя синхронизация массивов отключена;
- в формах людей старые записи доступны для просмотра, но не редактирования;
- изменение биографии/цитаты не затрагивает роли;
- несопоставленные исторические записи остаются видны без ссылки;
- намеренное удаление мигрированной роли из актуального состава убирает её из
  нового представления, но исходный массив и снимок переноса остаются в базе;
- физическое удаление спектакля обнуляет ссылку журнала, сохраняя историческую запись.

Возврат флага False возвращает старый интерфейс, но не является откатом данных:
добавленные строки состава остаются. Полный откат переноса требует проверенной
резервной копии. Старые поля в этом этапе не удаляются.

## Проверено в облачной среде

Предварительный анализ доступной базы: 23 актёра, 1 режиссёр, 116 однозначных записей,
16 несопоставленных. Реальные названия и роли в этот документ не включены.
На отдельной временной копии импорт сохранил все поля всех актёров/режиссёров
побайтово в сериализованном сравнении. Все 46 исходных строк состава остались;
после добавления недостающих ролей их стало 111. Повторный импорт не создал дубликатов.
В доступной исходной базе применена только миграция пустой таблицы; переноса нет,
флаг выключен. Это не проверка актуального production-сервера.

Тесты: `test_performance_relations.py` и `PerformanceCredits.test.tsx`.
Проверяются сохранность полей, неоднозначность, устаревший digest, откат транзакции,
переименование по ID, исторические записи и запрет старого редактирования массивов.
