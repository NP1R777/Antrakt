# Импорт отзывов VK

Импорт наполняет блок «Что говорят о нас». Подходящие новые отзывы публикуются
автоматически. Администратор управляет контентом, а обычное обновление не требует
его участия. Ручные правки имени/текста при следующем импорте заменяются из VK —
это согласованное поведение. Скрытие, закрепление и исключение сохраняются.

## Выбор публикаций и комментариев

- Обычный проход читает только последние 20 постов стены и ищет фразы-приглашения.
  Реестра старых постов и их постоянного перечитывания нет.
- Первый успешный проход и явный `--full` используют расширенный обход с пределом
  400 постов. Если стена больше, первые 400 обрабатываются, но результат отмечается
  неполным, а не успешным полным обходом.
- API загружает страницы верхнеуровневых комментариев с `preview_length=0`,
  `thread_items_count=0` и хронологическим порядком. `current_level_count`, если
  передан, определяет число комментариев нужного уровня. Вложенные ответы,
  удалённые комментарии и сообщения сообществ не публикуются как отзывы зрителей.
- HTML разбирается BeautifulSoup (`html.parser`), реальные VK ID извлекаются из
  контейнеров комментариев. Страница поста переиспользуется; распознаваемые ссылки
  следующей страницы комментариев обходятся до конца. Нераспознанная разметка,
  вход и капча не считаются пустой стеной или успешной загрузкой.
- Нет ID — комментарий пропускается с увеличением `skipped`, ID из текста не
  вычисляется. Исторические записи со старыми хешами не сливаются и не удаляются
  по похожести текста: их соответствие настоящим ID не доказано. Такие записи
  могут потребовать отдельного сопоставления, если на production уже есть дубли.
- Предел комментариев на пост — 10000, HTML-страниц — 200. Достижение предела даёт
  явный частичный результат. Уже сохранённые настоящие отзывы не удаляются.

## Конфигурация

Одинаковые настройки передаются backend и worker. Секреты — только в окружении.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `VK_GROUP_DOMAIN` | `tc_antrakt` | Короткий адрес сообщества |
| `VK_IMPORT_BACKEND` | `auto` | `auto`, `api`, `html` |
| `VK_ACCESS_TOKEN` | пусто | Доступ API; разрешения приложения проверяются отдельно |
| `VK_SESSION_COOKIE` | пусто | Cookie авторизованного доступа HTML |
| `VK_API_VERSION` | `5.199` | Версия API |
| `VK_IMPORT_INTERVAL_SECONDS` | `1209600` | Автообновление раз в 14 дней; `0` выключает расписание |
| `VK_IMPORT_MAX_ATTEMPTS` | `3` | Максимум попыток задания, включая восстановление после падения |
| `VK_IMPORT_STALE_SECONDS` | `300` | Когда прерванное running-задание можно проверить на восстановление |
| `VK_IMPORT_MAX_COMMENTS` | `10000` | Предел комментариев на пост (минимум 100) |
| `VK_IMPORT_HTTP_ATTEMPTS` | `3` | Ограниченные повторы сетевых ошибок и временных ошибок API |
| `VK_IMPORT_REQUEST_INTERVAL` | `0.35` | Минимальный интервал между запросами, секунды |
| `VK_IMPORT_CA_BUNDLE` | пусто | Необязательный дополнительный доверенный PEM CA |

`auto` сохраняет прежний приоритет cookie, затем API. Явный `api` рекомендуется
после проверки реального токена. Автоматического переключения между источниками
при ошибке нет: оно могло бы скрыть проблему доступа. Без настроенных доступов
worker не создаёт плановые задания, сайт продолжает работать, админка показывает
«не настроено».

TLS проверяется всегда, с системными CA и certifi. `VK_SSL_VERIFY=False` больше
не отключает проверку. Токен передаётся в теле POST; cookie не пересылается на
посторонние домены при редиректе. В клиентские ошибки не включаются секреты,
сырой ответ VK и тексты неожиданных исключений.

## Очередь, расписание и восстановление

Production Compose запускает отдельный `vk-reviews-worker`. Он проверяет очередь
каждые 5 секунд. На пустой истории задание создаётся сразу при наличии доступов;
для существующих установок учитывается прежний `last_run_at`. После терминального
результата следующий плановый запуск — через заданный интервал. Сетевые/временные
ошибки получают ограниченные повторы через 30, 60… секунд. Постоянные ошибки
доступа не вызывают бесконечных повторов. Кнопка обновления остаётся доступной
для внепланового запуска после исправления конфигурации.

`VkImportJob` хранит состояние (`pending`, `running`, `success`, `partial`,
`failed`), этап, попытки, счётчики, время активности, завершение и безопасную ошибку.
Счётчики обработок накапливаются за все попытки: повторное чтение после сбоя
увеличивает `scanned/comments/unchanged`, но не создаёт дубли и не увеличивает
`added` второй раз. Сохранение отзыва и соответствующего прогресса — одна короткая
транзакция. На время сетевого запроса транзакция не держится.

Уникальное ограничение допускает одно активное задание на группу. Session advisory
lock PostgreSQL не позволяет двум процессам импортировать её одновременно.
Устаревший heartbeat сам по себе не позволяет отобрать задание у ещё работающего
процесса: требуется свободная session lock. После остановки процесса PostgreSQL
освобождает lock, а stale-задание восстанавливается в пределах лимита попыток.
Внешний pooler с transaction pooling для этой session lock использовать нельзя.

Кнопка, расписание и CLI используют одну очередь/блокировку. Старый внешний cron
`parse_vk_reviews` следует отключить при включении расписания worker, чтобы не
создавать лишние внеплановые задания (одновременный импорт всё равно исключён).

```sh
# Worker обычно запускается обычным production up -d --build.
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build backend vk-reviews-worker
# Ручной синхронный запуск: ошибке соответствует ненулевой exit code.
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T backend python manage.py parse_vk_reviews
# Один проход фонового обработчика, полезно для диагностики.
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T backend python manage.py vk_reviews_worker --once
```

В development worker включается профилем `vk`:
`docker compose --profile vk up -d --build`. Backend и worker получают одинаковые
VK-настройки из окружения Compose; после изменения их следует пересоздать.

## API и управление отзывами

- `POST /vk-reviews/parse/` — только superuser, HTTP 202, `{job, created}`.
  При активном задании возвращается оно же. Неполученные доступы — HTTP 400.
- `GET /vk-reviews/parse/` — только superuser, состояние настройки, последний
  запуск, последний успех и интервал. Это не проверка токена реальным запросом.
- `DELETE /site-review<ID>/` для импортированного отзыва ставит `excluded=True`.
  Запись и исходные ID сохраняются; повторный импорт не восстанавливает её.
  Явное восстановление: `PUT` с `excluded=False`. Ручной отзыв без VK ID удаляется
  физически. Django admin придерживается тех же правил исключения.
- Публичный список не возвращает скрытые/исключённые отзывы, максимум 6:
  сначала закреплённые по `position`, затем новые. Неизвестные даты идут в конце.
- У VK нет звёздной оценки: rating отсутствует; frontend не показывает звёзды даже
  для старого ответа с rating=5. Ручная настоящая оценка допустима от 1 до 5.
- Админка показывает статус и источник, позволяет менять порядок закрепления и
  восстановить исключённый отзыв. Завершение импорта не затирает несохранённые
  поля: после сохранения можно обновить список. Это не защита правок от VK-импорта.

## Миграции и данные

0027 добавляет исключение, задания, привязку состояния к группе и nullable rating.
0028 удаляет только точные оригинальные шесть записей из 0016: проверяются имя,
роль, текст, дата, source=manual, rating=5, пустые source/avatar URL и отсутствие
всех VK ID. Изменённые или неоднозначные записи не удаляются. Все настоящие ручные
отзывы сохраняются. Импортированным VK-записям rating сбрасывается в NULL.
При откате вымышленные отзывы не создаются заново. До production-обновления нужен
обычный backup базы. Актёры, состав, спектакли, фотографии и их автоматизация
этими миграциями не меняются.

## Проверки и границы

`manage.py test my_app1.test_vk_parser` проверяет сеть на подменённых ответах,
пагинацию, ID, ошибки, даты, очистку, публикацию, исключение, очередь, конкуренцию
и восстановление на отдельной PostgreSQL БД. Frontend-проверки:
`SiteReviewsPageAdmin.test.tsx` и `Testimonials.test.tsx`.

Живой API-токен и авторизованная HTML-разметка production в облаке не проверены:
реальные cookie/токены для этих проверок не использовались. Перед развёртыванием
проверить реальный выбранный режим, полные тексты, количество отзывов и источник.
Спецификация: https://github.com/VKCOM/vk-api-schema (wall methods/responses 5.199).

Локальная проверка реализации 29.10.2026: 153 backend-теста прошли в production-
образе Python 3.11 с отдельной тестовой PostgreSQL БД; 32 релевантных frontend-
теста (8 наборов) прошли, включая 7 новых проверок отзывов. TypeScript и сборка
успешны; сохраняются прежние предупреждения сборки и тестовых библиотек.
Два старых проблемных frontend-набора App/stringMatching не включались.
Compose dev/prod проверены с искусственной конфигурацией без чтения .env.prod.
Chromium: очередь/статус, несохранённые поля, сохранение, источник без звёзд,
ненастроенный VK и мобильный экран 390 px. API в браузере подменялся.
Отдельный процесс worker проверен с 150 искусственными комментариями: SIGKILL
после первых 100, затем восстановление, 150 уникальных записей и added=150.
Временная smoke-БД удалена; рабочая БД и данные production не менялись.
