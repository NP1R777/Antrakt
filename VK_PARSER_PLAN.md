# План доработки VK-парсера

План по решениям владельца от 29 октября 2026 года. Реализация подготовлена локально; живая интеграция с production VK требует проверки доступов.
Коммиты и отправка на GitHub требуют отдельного разрешения владельца.

## Согласованные границы

- Реализовать пункты аудита 1, 4, 5, 7, 8, 9, 10, 11.
- Обычный импорт по-прежнему ищет приглашения среди последних 20 постов.
  Не вести реестр старых постов для постоянного перечитывания. Существующий
  расширенный первый запуск и явный --full сохранить.
- Не разделять исходный текст и редакторские правки: повторный импорт по-прежнему
  обновляет имя/текст из VK. Защита ручных редакторских переопределений отложена.
- Не вводить премодерацию: подходящие новые отзывы публикуются автоматически.
- Сохранить ручное скрытие, закрепление, добавление и исключение отзывов.
- Не менять автоматику переноса спектаклей и назначения ролей.
- Удалить только шесть заранее написанных отзывов из миграции 0016.

## Этап 1. Корректность получения данных

1. Добавить пагинацию комментариев API и preview_length=0; ограничение объёма
   должно давать явный неполный результат, а не сообщение о полном успехе.
2. Сохранять текущую выборку верхнеуровневых комментариев; не смешивать ответы
   театра в ветках с самостоятельными отзывами. Вложенные ответы автоматически
   не включать в публикацию.
3. Ввести явный выбор API/HTML, сохранив совместимость существующих настроек.
   Перевод на основной API выполнить после проверки реального доступа; не ломать
   работающий cookie-режим из-за неподтверждённого токена.
4. Исправить структурный разбор HTML, извлекать стабильные реальные ID, исключить
   ID из хеша изменяемого текста. Если ID не извлечён, пропускать с диагностикой.
   Существующие записи со старыми хешами не объединять/удалять по похожести текста.
5. Переиспользовать страницу поста вместо повторного запроса. Проверять ответы:
   вход, капча, ограничения и повреждённый ответ — ошибки, не пустая стена.
6. Добавить ограниченные повторы временных ошибок и соблюдение ограничений VK,
   безопасные сообщения об ошибках, проверку TLS без возможности её отключить.
7. Использовать часовой пояс проекта; неизвестные даты не выдумывать,
   сортировать отсутствующие даты после известных.

## Этап 2. Сохранность и достоверность отзывов

1. Сохранять отметку исключения импортированного отзыва по реальным VK ID,
   чтобы удалённый администратором комментарий не возвращался при импорте.
   Сохранить возможность явного восстановления. Скрытие и закрепление сохранять.
2. Недоступность исходного комментария не считать основанием удалять сохранённый
   отзыв; удаление настоящих отзывов из рабочей БД не входит в очистку демоданных.
3. Убрать автоматически присвоенные пять звёзд у VK-комментариев. Рейтинг без
   подтверждённой оценки не показывать; корректные ручные оценки сохранять.
4. Показать ссылку на оригинальный комментарий (при наличии ID) и источник VK.
5. Добавить новую миграцию, удаляющую шесть известных демоотзывов по точному
   набору исходных полей и отсутствию VK ID, без удаления по одному имени или
   всех source=manual. Не переписывать применённую историю миграций. Проверить,
   что новая установка после всех миграций также не содержит этих отзывов.
   Изменённые/неоднозначные совпадения не удалять автоматически.

## Этап 3. Автономный фоновый запуск

1. Хранить задания и отчёт в PostgreSQL, обрабатывать отдельным worker без
   обязательных Redis/Celery. API только ставит задачу и возвращает её ID.
2. Исключить одновременный импорт одной группы из API, команды и расписания.
   Предусмотреть восстановление после падения worker, ограниченные попытки и
   безопасное продолжение без дублей; не держать транзакцию на время сети.
3. Записывать данные небольшими транзакциями и показывать частичный результат
   честно. Не отмечать первый проход завершённым при недостоверном ответе/сбое.
4. Сохранять этап, прогресс, счётчики новых/обновлённых/пропущенных, последнюю
   ошибку и время последнего успеха. Ошибки CLI возвращают ненулевой exit code.
5. Настроить автоматический запуск с изменяемым интервалом; исходный ориентир
   из текущей документации — раз в две недели. При отсутствии доступов VK
   показывать «не настроено», не мешая работе остальных частей сайта.
6. Подключить worker к production Compose; сохранить проект, существующие тома
   и promote-worker. Проверить перезапуск, доступы и документацию развёртывания.

## Этап 4. Интерфейс и проверки

1. Кнопка обновления и просмотр статуса фонового задания; обычное автоматическое
   обновление не требует посещения админки. Защита от сброса несохранённых правок
   при обновлении списка, без защиты правок от следующего импорта VK.
2. Управление порядком закреплённых отзывов, отображение источника, ссылки,
   статуса и ошибок; текущие скрытие/закрепление/ручное добавление сохраняются.
3. Тесты: >100 комментариев, длинный текст, последние 20 постов, HTML ID,
   повторный импорт, исключения, отсутствие премодерации, ложный успех, даты,
   очистка только демоданных, ограничения доступа, конкуренция и восстановление.
4. Backend-тесты на отдельной PostgreSQL БД; релевантные frontend-тесты,
   TypeScript, production-сборка, проверка интерфейса и изолированный worker smoke test.
5. Реальный API и cookie-HTML отдельно проверить при наличии действующих доступов.
   Тесты с подменёнными ответами не считать доказательством реальной интеграции.

Результат и эксплуатация описаны в VK_PARSER.md. Production-данные не изменялись; миграции проверены на отдельных базах.
