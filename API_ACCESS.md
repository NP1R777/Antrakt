# Права доступа к API

Роль администратора сайта определяется `is_superuser`; одного `is_staff` недостаточно.

| Данные / операция | Гость | Пользователь | Администратор |
| --- | --- | --- | --- |
| Публичные списки и карточки контента | Чтение | Чтение | Чтение |
| Создание, изменение, мягкое и полное удаление контента | Нет | Нет | Да |
| Списки `*-admin`, пользователи, модерация отзывов | Нет | Нет | Да |
| Даты рождения и варианты поздравлений в редакторе | Нет | Нет | Да |
| Поздравление на сегодня, выбранные отзывы и тексты сайта | Чтение | Чтение | Чтение и управление |
| Запуск импорта отзывов VK | Нет | Нет | Да |
| Профиль | Нет | Только свой | Любой |
| Отзывы под публичными карточками | Чтение | Создание, удаление своих, реакции | Также модерация |
| Загрузка изображений | Нет | Только аватар в собственной папке | Также изображения контента |
| Удаление файлов хранилища | Нет | Только собственная папка аватаров | Любой файл в настроенном хранилище |

Неавторизованный запрос к закрытой операции получает 401, запрос пользователя без
необходимой роли — 403. Удалённые карточки и неопубликованные новости, включая их
отзывы, возвращают посетителям 404. Администратор сохраняет доступ для редактирования
и восстановления. Удалённые отзывы не принимают новые реакции.

По умолчанию DRF использует `ReadOnlyOrSuperUser`. Публичные операции регистрации,
входа и восстановления доступа, а также пользовательские операции имеют собственные
разрешения. Новые административные списки нужно явно закрывать `IsSuperUser`:
проверка интерфейса React не заменяет проверку Django.

Профиль не позволяет обычному пользователю изменять роль, дату создания, `deleted_at`
или пароль. Для смены пароля предназначен отдельный API с проверкой текущего пароля.

Загрузка аватара использует `folder=profile`; сервер сам подставляет ID владельца:
`profile/<user_id>/<uuid>.<extension>`. Выбор чужой папки и фиксированного имени
пользователю запрещён. Удаление проверяет адрес настроенного хранилища и папку владельца.
Старые файлы не перемещаются: снятие аватара в интерфейсе отвязывает его от профиля,
не удаляя файл. Сохранение профиля обязательно для применения этого изменения.

Проверки прав и границ доступа находятся в `backend/app/my_app1/test_api_permissions.py`.
Запуск из `backend/app`:

```sh
USE_MINIO_STORAGE=False ../venv/bin/python manage.py test my_app1 --noinput
```

В тестах файловых операций S3 подменяется: они проверяют права, ключи объектов и
отсутствие вызовов хранилища при отказе. Это не интеграционная проверка MinIO.
Первый этап прав API не требовал миграции БД.

## Удалённые аккаунты и отзыв сеансов

Миграция `0024_user_auth_version` добавляет служебную версию авторизации. Перед
запуском обновлённого приложения выполните `python manage.py migrate --noinput`.
При первом внедрении этой версии все пользователи должны войти заново: JWT без
версии авторизации больше не принимаются. Django-сессии также потребуют нового входа.

Аккаунт с `deleted_at` не может входить по email или телефону, пользоваться JWT,
обновлять refresh-токен или запрашивать восстановление пароля. Версия авторизации
изменяется при удалении, восстановлении и смене пароля. Прежние JWT и Django-сессии
не оживают после восстановления аккаунта; нужен новый вход. Обычное редактирование
профиля не завершает сеансы. Служебная версия не доступна для изменения через API.

Изменения жизненного цикла сохраняются через `User.save()` / `set_password()` +
`save()`. Не используйте `QuerySet.update()`, `bulk_update()` или сырой SQL для смены
пароля и удаления/восстановления пользователей: они обходят модельный механизм
отзыва. Физическое удаление аккаунта тоже приводит к отказу старых JWT с 401.

Для старых колонок `access_token` / `refresh_token` больше не сохраняются новые JWT.
Источником проверки служат подпись JWT, состояние пользователя, версия авторизации
и blacklist refresh-токенов. При смене состояния старые сохранённые значения очищаются.

Фронтенд объединяет одновременные запросы обновления токена. Отказ обновления
очищает локальные данные авторизации и уведомляет React; запросы входа и выхода не
запускают обновление повторно. Завершённый запрос refresh не возвращает пользователя
в сеанс, если он успел выйти.

Проверки: `test_account_sessions.py` использует настоящие JWT и Django-сессии;
`src/services/AuthService.test.ts` проверяет поведение клиента при отзыве сеанса.
## Восстановление пароля

`POST /password-reset/` принимает `{email}` и отвечает одинаковым сообщением для
существующих, неизвестных и удалённых аккаунтов, включая ошибку доставки почты.
Пароль и текущие сеансы на этом шаге не меняются. Ошибка SMTP фиксируется на сервере
без адреса, текста исключения и секретной ссылки.

Письмо содержит ссылку на `FRONTEND_BASE_URL/reset-password#uid=…&token=…`. Параметры
после `#` читает React; они не передаются nginx/Caddy в HTTP-запросе страницы.
Адрес берётся из конфигурации, а не из заголовка Host запроса. В продакшене нужен
корректный HTTPS `FRONTEND_BASE_URL` и настроенный SMTP. В локальных тестах почта
сохраняется в памяти; реальная доставка SMTP этими тестами не проверяется.

`POST /password-reset/confirm/` принимает `{uid, token, new_password}`. Сервер
проверяет подпись Django, срок 30 минут, активность аккаунта и требования к паролю
с учётом пользователя. Сохранение выполняется под блокировкой строки пользователя:
повторное использование ссылки, включая одновременные запросы, не допускается.
Изменение пароля отзывает JWT и Django-сессии через `auth_version`. Ссылка также
перестаёт работать после удаления/восстановления аккаунта. Ошибка качества пароля
не расходует ссылку. Сброс не выполняет автоматический вход.

Лимиты на час: 3 запроса письма на email и 20 на IP; подтверждение — 60 на IP.
Они одинаково применяются к неизвестным адресам. Ответ 429 содержит Retry-After.
Счётчики хранятся в PostgreSQL, общие для Gunicorn-процессов; вместо IP/email
сохраняется HMAC. Неиспользуемые счётчики старше суток очищаются при запросах.
Для этого требуется миграция `0025_password_reset_limits`.

Локально IP определяется по REMOTE_ADDR (`TRUSTED_PROXY_COUNT=0`). В production
Compose задан `TRUSTED_PROXY_COUNT=1`, так как публичный API доступен только через
Caddy. Не открывайте backend напрямую с этим значением. При изменении цепочки
доверенных прокси настройку нужно пересмотреть.

Страница React показывает ошибки пароля, подтверждение успеха и кнопку входа.
Для недействительной ссылки доступен повторный запрос письма. Запрос восстановления
из личного кабинета не разлогинивает пользователя. Глобальный JWT-interceptor не
мешает этой публичной странице.

Дополнительные проверки находятся в `test_password_reset.py` и
`src/pages/ResetPasswordPage.test.tsx`; тесты формы изолируют рендеринг Chakra из-за
существующей проблемы разрешения зависимостей CRA/Jest.

## Фоновый импорт VK

POST /vk-reviews/parse/ доступен только superuser и возвращает HTTP 202 с заданием, а не готовые отзывы. GET того же адреса показывает конфигурацию и результат. Worker выполняет сеть отдельно. DELETE импортированного site-review исключает его без физического удаления; PUT excluded=false восстанавливает. См. VK_PARSER.md.
